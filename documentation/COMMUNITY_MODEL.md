# CHAOSOS community model

## Feedback is part of development

The project explicitly welcomes negative feedback. A report does not need to
praise the project or soften a technical criticism. The useful core is:

1. What is the problem?
2. Where and when does it happen?
3. What result did you expect?
4. What change would you make?
5. Can you provide a screenshot, log, or reproduction?

## Maintainer decision

Reports are triaged as bug, security issue, feature request, design issue, or
out-of-scope. The maintainer may accept, reject, defer, or ask for evidence.
Rejection should include a reason when practical.

## Forks

A community developer may produce a distinct operating environment from
CHAOSOS, select a new name, and change the user interface. Preserve the
applicable original attribution notices and describe the source relationship.
The original project name does not need to remain the derivative's primary
product name. See `DERIVATIVE_PROJECTS.md`.
